# Project model

## Principle

A project is a local folder that gathers the story's identity and its materials. The fixed structure takes care of what every story shares; content formats can grow without requiring every story to be a book.

## Location

By default, new projects live in `Documents/Plotcraft` (the documents directory provided by the operating system, inside the `Plotcraft` folder). The base folder can be changed in **Preferences → Projects folder**. The change applies to projects created after it; existing projects stay where they were created. The library keeps each project's path and can therefore gather projects from different places.

Each project gets its own subfolder, with a name derived from the title and a stable identifier. Changing the title later does not require renaming the folder. The project must stay readable when copied to another computer, because the absolute path is not part of its manifest.

## Initial structure

```text
Documents/Plotcraft/
  salt-cities-<id>/
    project.json
    covers/
    gallery/
    content/
      book/
        book.json
        manuscript.delta.json
        manuscript.md
        chapters/
      narrative/
        types.json
        elements/
        attachments/
```

- `project.json` holds the common metadata and the schema version.
- `covers/` stores the imported cover, when one is chosen. While there is no cover file, `coverIndex` identifies a visual cover generated by the interface.
- `gallery/` gathers reference images and visual material for the story. `gallery/index.json` gives each image a stable ID (`g_...`), so that elements and text refer to it without using a path. Files placed in the folder by hand get an ID on the next read; if a file disappears, its entry stays in the index and the image shows as missing until it comes back.
- Each book document (the single manuscript or a chapter) has two files: `<name>.delta.json`, the **source of truth** (the editor's Delta format, with fonts, colors, alignment, mentions and images), and `<name>.md`, a readable copy generated from it. Color, font and alignment have no form in Markdown and live only in the Delta. Changing the `.md` from outside does not change the book.
- `content/book/book.json` defines whether the book uses a single manuscript or chapters and, in that case, stores their order and titles. Each chapter is a Markdown file in `content/book/chapters/<id>.md`.
- `content/narrative/elements/` holds one JSON per narrative element (character, place, object...). They all share the same structure; the type is an ID that points to an element type.
- `content/narrative/types.json` holds the **custom** element types. The eight built-in types (`character`, `place`, `object`, `creature`, `organization`, `event`, `concept` and `note`) live in the code, with stable IDs, and are not written to disk.
- `content/narrative/attachments/<element id>/` holds the copies of the images the person attached to an element from the computer.

## Book document format

`<name>.delta.json` stores `{schemaVersion: 1, ops: [...]}`. Besides the editor's standard format, it uses: the `mention` attribute (`{id, name}`) on text linked to an element; the `gallery-image` embed (`{id, width?, align?}`), which points to a gallery image by ID; and the `divider` embed. Projects that only have the `.md` (earlier versions) are converted on first open: the original Markdown is copied to `content/book/migration-backup/` (without overwriting) and the `.delta.json` is created; if the `.delta.json` is damaged, the chapter is read again from the `.md` and the damaged file is left as it is. When chapters are joined into a single manuscript, each chapter gets its title as a heading, if it does not have one yet.

## Project fonts

The `fonts/` folder stores `.ttf`, `.otf` or `.ttc` files added by the person, which travel with the project. The editor also offers the bundled fonts and the ones installed on the computer. Text that uses a font the computer does not have shows a warning, and the font can be added to the project.

## Book and chapters

The initial mode is a **single manuscript**. Earlier projects, which do not have a `book.json` yet, stay in that mode and read `manuscript.md` as usual. When chapters are turned on, the current text is copied to the first chapter. When going back to a single manuscript, the chapters are joined, with titles, into `manuscript.md`. The conversion preserves the source files. Removing a chapter takes it out of the active index and moves its files (`.delta.json` and `.md`) to `content/book/archive/`. The editor lets you add, rename and reorder chapters.

**Reading mode** shows the book the way a reader would see it: one chapter at a time, a narrow column, adjustable text size (14 to 30), a progress bar for the whole book, ← → arrows to change chapter, and mentions that open the element with a click (and show its card on hover). It reads the current text of the buffers, including what has not been saved yet, and remembers the chapter and the size per project on this computer. It opens from the book button in the chapter panel or in the editor toolbar, and works in full screen.

The editor writes Markdown to files that can be read outside Plotcraft. It offers formatting, find and replace, undo and redo history, preview, split view, autosave and a full-screen mode for the window. On macOS, the editing field queries the native spell checker through `NSSpellChecker`; on Android and iOS it uses Flutter's service. The spell-checking service for Windows and Linux still depends on a specific native integration.

## Narrative elements and references

### Element types
A type has an `id`, a name, an icon (`{set, name}` from the `icons_flutter` package, never the glyph code), a color (`#RRGGBB`) and a list of details (`fields`). Each detail has an `id`, a label and a kind: short text, long text, number, date, choice (with options), yes/no, another element or link. The built-in types ship with default details and translated labels. A custom type can only be deleted when no element uses it.

### Element (`schemaVersion` 2)
Fields: `id`, `typeId`, `title`, `aliases` (other names, also used to detect mentions), `summary`, `tags`, `icon` and `color` (override the type's, optional), `images`, `fields` (values of the type's details, by ID), `sections` (Markdown text), `phases`, `relations`, `mentionPolicy` (`auto` and `ignoredTerms`), `time` (optional), `createdAt` and `updatedAt`.

- **Images:** each item is `{ref: gallery, id}` (a gallery image by ID) or `{ref: attachment, file}` (a copy in `attachments/`, with a path relative to the project). The first image is the cover. When the element is saved, copies it no longer uses are deleted.
- **Phases:** show how the element changes over the story. Each phase has a title, a description, an `anchor` (`chapter` with the chapter ID, `manual` with free text, or `none`), `fieldOverrides` (details that change in that phase) and `image` (one of the element's images).
- **Relations:** `{id, targetId, label, reciprocalLabel, note}`. They are stored only on the source element; the other side sees the relation through an index derived in memory (with the reciprocal label, or the same label if there is none). Relations to elements that no longer exist are ignored and removed on save.
- **Details that point to elements:** a detail of kind `element` (one) or `elements` (several) stores IDs of other elements, separated by commas, and can limit the accepted types (`targetTypes`). An event's "Where" accepts several places, an object's "Owner" and an organization's "Leader" accept a character, and a creature's "Habitat" accepts places. These details become links on the map and show up as "Cited in the details of" on the element they point to. Text from earlier versions stays readable: a name that matches an element's title or alias is recognized, and what does not match shows as text until it is replaced.
- **Story time (`time`):** when the element happens in the story's world, as `{label, position}`. The `label` is free text, written the way the story tells it ("Year 312", "summer of 1987", "three days before"), with no calendar required. The `position` is an optional number used only for ordering (larger = later). Without `time`, an event with the "when" detail filled in shows up in the chronology without a position.
- **Mentions:** are not stored on the element. The policy (`mentionPolicy`) says whether names and aliases are highlighted in the text and which terms to ignore.

### Old elements (`schemaVersion` 1)
Old files have a free-text `kind`. They stay readable: the `kind` becomes the `typeId`. When the value is not a known type (for example `Dragon`), a custom type with that name is created and saved in `types.json`. The element files are not changed until the element is edited and saved.

### References in the text
The editor inserts references with the syntax `[[element:<id>|displayed name]]`. The ID stays valid when the element is renamed. The preview turns the reference into a link that opens the element, and the element shows in which documents it is cited. An extension pipeline turns custom syntaxes into something the preview can show without changing the source Markdown. When an element is removed, its JSON is moved to `content/narrative/archive/`; the marks already written stay in the text for recovery or updating.

## Common metadata

The manifest holds `schemaVersion`, `id`, `title`, `subtitle`, `author`, `description`, `genre`, `tags`, `createdAt`, `updatedAt`, `primaryFormat`, `coverIndex` and `coverFile`. The additional identity fields are optional. The imported cover, when there is one, is copied to `covers/` and referenced by a path relative to the project. `primaryFormat` starts as `book`. Dates use ISO 8601. Earlier manifests, without these fields, stay readable with empty values.

On creation, the title must be 3 to 120 characters long. Subtitle, author, genre and description are limited to 160, 120, 80 and 2,000 characters, respectively. Up to eight distinct keywords of up to 40 characters each are accepted. Imported covers can be PNG, JPEG or WebP, up to 10 MB. Validation happens before the project is written to disk.

The manifest is the source of each project's data. Preferences only store the list of folder paths so the library can find projects in different directories. No project file should depend on an absolute path saved in the manifest.

## Project types

The manifest's `primaryFormat` says what kind of story the project is and is chosen on creation (it does not change afterwards). The types live in a registry (`ProjectFormats`):

- `book` (book or novel): has a manuscript, with chapters or a single text, plus elements and a gallery.
- `manga`: for now a skeleton, with only an overview, elements and a gallery. It does not create `content/book/` and the workspace does not show the manuscript. Pages and panels do not have a model or an editor yet.

An unknown `primaryFormat` (from a newer version) opens as a book. The library shows the type's icon on each card and, when there is more than one type, lets you filter by it. The project overview summarizes type, words, chapters, elements and images. Audiobooks and other formats can occupy new directories inside `content/` and join the registry.

## Current lifecycle

Creating a project writes the initial structure to disk and opens its workspace. Saving the manuscript or a chapter updates `updatedAt` in the manifest. From the overview you can edit title, subtitle, author, genre, description, keywords and cover; the cover image is copied to `covers/` and the manifest is updated. Dates and the folder are data generated by the system. The overview shows previews of the gallery images. You can add images through the interface, which copies the files to `gallery/` without replacing existing names, remove them with confirmation, or place them directly in that folder and refresh the gallery. Deleting a project removes its folder and all its content, after confirmation in the library. Projects from earlier versions, previously saved only in the preferences, are migrated to folders when the library loads.

The app also ships a complete sample story, which is copied into the projects folder on request and from then on is an ordinary project (see [Application architecture](architecture.md)).
